- ~~bug 不替报告人关：修好发版后，回复请报告人更新验证，他确认了自己关~~ ⚠️更正（11-24 #63 主人定）：**bug 修好发版后就回复并关掉**，回复结尾写明「更新后如果还有问题，欢迎另开一个新 issue 并附上日志」，以「已完成」关闭。建议类婉拒后以「不计划」关闭（11-27 #64 主人定：「婉拒然后关了吧」；#44、#47 也是这样关的）。报告人自己配套提了 PR、合并发版的，跟着 PR 一起回复并关掉（11-24 #56/#57）
- **需求类做完、发了版就关**（主人 11-18 发 2.6.0 后定）：按标题判断，issue 要的功能这一版已经做到（如「是否可以添加自定义虚拟屏」），回复讲清怎么用、怎么更新，结尾说明「需求已经实现，这个 issue 先关闭；使用中遇到问题，欢迎另开 issue 反馈」，以「已完成」关闭。只做到一部分的不关
- **婉拒要平和**：讲清为什么不做：是产品定位不同，不是不想做、不是甩锅、不是做不到；能指向现成的好方案就指过去。第一版 #4 回复被主人评为「有点太严厉了」
- **做不到的要论证闭环**（11-16 #9）：不只给结论，要讲清怎么实测、看到了什么、怎么排除其他解释、为什么只剩这条路而这条路不走。主人原话：「说明我们是怎么实测得到这个结论的，过程要讲清楚，不要只讲结果，让整个论证逻辑闭环」
- 同一个问题的新 issue（如 #11 之于 #9）：致谢，链接到已经详细回复的那条，再用一段话概括结论
- 没验证的推测在回复里要么不写，要么标明是推测
- **以主人的第一人称写**（11-21 #47 主人纠正）：回复是主人本人在说话，用「我」，不写「作者」「我们决定」这类第三方视角
- 主人看过方向后说「直接发」「发」「回复他」，就不用再把草稿给他审一遍
- **不加 issue 模板**（11-21 主人定）：加过表单又撤了，issue 自己逐条回，缺信息时再追问；等实在回复不过来再考虑。使用问题可引到讨论区（已开，#50 置顶）

**Why:** 2026-11-15 处理 #3（bug）和 #4（婉拒）时主人定的基本做法；11-16 回 #9 时主人要求把论证讲完整。

**How to apply:** 写 issue 回复用书面语、先致谢；修好发版的 bug、做完发版的需求都回复后关掉，有问题请对方另开新 issue。产品边界见 [[project-product]]，文案风格见 [[feedback-doc-writing]]
