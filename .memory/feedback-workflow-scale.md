1. **起之前先确认**：说清打算几个 agent、各干什么、为什么值得，主人点头再起（ultracode 开着也一样）
2. **默认自己干**：读代码、设计、实现自己小步快跑（主人：「你一个人的能力也是很强的」）
   - **设计、原型类的活绝不起 Workflow**（11-24，#61 融合方案我派了 5 个 agent 头脑风暴、跑了 22 分钟）：直接画原型给主人看，跟主人快速迭代。主人：「做原型的目的就是小步快跑，你派一个 workflow 出去头脑风暴，那不是拖慢了吗？头脑风暴的效果还没有我和你去快速迭代原型的效果好」
3. **小改动不审**：几十行、单一逻辑单元的 bug 修复，测试、门禁过了就收工，连「要不要审」都别问（「不要大炮打蚊子」）。根因和复现已查清的 bug，设计阶段也不起 Workflow（11-18：「直接干就行。干完咱们直接测，测完就发版」）
   - **更新日志、issue 回复、README 这类文案活不审**（11-27 发 2.10.0，ultracode 开着我要起 4+1 审文案，被打断：「这是小工作，审啥，没必要」）：照 [[feedback-doc-writing]] 自己写完直接发
4. **审查只审一轮**：修掉核实过的问题就收工，不起复审（AGENTS.md「审到再无新发现」在这里让位）。例外：接手外部 PR 时先审原 PR，改完再轻量审一轮
5. **规模**：一次 5 个左右，并行分析 → 一个核实者统一核实；不要每条 finding 派反驳者、不要多轮长链
6. **维度要全**：正确性之外，必须同时审架构（分层、依赖方向、职责边界、扩展性）、工程审美（干净、状态机清晰、命名与规模、过度防御/设计）、去冗余（死代码、重复逻辑、文档与代码不符）；别在提示里写「不报风格偏好」

**Why:** 主人 11-13：「一定要注意控制 agent 的数量，可千万不要把额度给打爆炸了」「链路太长了就会很慢」；11-14：「以后起 workflow 去做任何事之前，你得先跟我确认」。
**How to apply:** 想起 Workflow 时先停下问一句；没确认就自己做。编排 skill 见 [[skill-routing-general]]。
